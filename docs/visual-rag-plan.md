# План исправления visual RAG

Ветка: `fix/visual-rag-evidence`, база: `main` (`d5bb245`).
Работаем без API-ключей и без запуска моделей. Старые чанки не переписываем.

1. **Диагностика существующих данных (первый шаг).** Показать выбранный набор
   чанков, типы, версии, результаты BM25 и точный контекст для LLM. Проверять
   контрольную сумму JSONL, если она есть в manifest. Добавить offline CLI,
   тесты и воспроизвести поиск на travel.zip. Не менять ранжирование вслепую.
   Реализовано: `python -m app.rag.inspect "вопрос" --documents-root PATH
   --chunks-dir PATH --output tmp/report.json`. Команда не читает `.env`,
   не вызывает LLM и не меняет исходные чанки. В реальном запуске бота
   использует настройки, переданные явно через `--top-k` / `--min-score`.
   По умолчанию top-k=2 и min-score=0, как в текущем конфиге бота.
   На travel.zip выбран `chunk-371860ed2778fea88cdf`: 27 чанков.
   Воспроизведено: вопрос о согласовании находит схему (стр. 4), вопрос о
   значке вложения — текст стр. 7/15, вопрос об описании схемы — оглавление
   стр. 2/3. Исходная точка для дальнейшего измеримого улучшения поиска.
2. **Сохранение доказательств.** Сохранять изображения и связь chunk → element →
   asset/page/bbox. Не удалять единственную копию вырезки. Старые чанки без
   asset_ids должны продолжать загружаться. Проверки на fixtures без моделей.
   Реализовано для новых извлечений: относительные пути `images/…`, SHA-256,
   страницы и bbox, source/element/asset IDs в чанках, сохранение при merge/split,
   перенос в загрузчик, проверка ассетов перед публикацией и при чтении кэша.
   Версия извлечения увеличена до 2. Старые чанки не переписываются: для заполнения
   отсутствующих связей нужен будущий повторный запуск владельцем ключа.
   Проверка сохранения/кэша выполнена через реальный extract_version с заменой
   границы парсера и модели тестовыми функциями (без Docling и API).
   Контрольные вопросы пользователя записаны в `docs/travel-evaluation.md`.
3. **Контроль полноты.** Разделить успешное выполнение и качество извлечения;
   сохранять raw analysis, unresolved/conflicts и решения о принятии. Проверить
   восстановление пропущенных источников и fallback после неудачного vision.
   Реализовано offline: восстановление всех пропущенных/частично выбранных
   источников, включая пустой результат chunker; raw-ответ и структурированный
   аудит в normalized.json. Partial/conflicts/unresolved/limitations,
   review_required/replacement и нечитаемые подписи/стрелки отправляют регион
   на проверку целиком, не в доказательства ответа. Это консервативное правило,
   а не подтверждение истинности остальных ответов vision.
   Ошибка картинки запускает page fallback даже при наличии заголовка.
   Имя файла больше не подменяет содержимое нечитаемой standalone-картинки.
   Manifest разделяет status (выполнение) и quality.status (passed_checks /
   needs_review), с покрытием только известных извлечённых источников.
   Загрузчик предупреждает о needs_review, но сохраняет доступ к остальным
   принятым фрагментам. Старые наборы без quality не считаются проверенными.
   Версия извлечения 3; старые данные не пересоздавались.
4. **Поисковое представление.** Разделить исходные доказательства и краткое
   поисковое описание. Добавить измеримый набор русских визуальных вопросов.
   Сравнить top-k на готовых чанках; новые описания не выдумывать вручную.
   Реализован отдельный слой лексических подсказок: типы визуальных объектов,
   небольшой словарь терминов paperclip/icon и др., нормализация запросов,
   понижение оглавления. Исходный chunk.text и контекст LLM не меняются.
   Навигационный заголовок с реальными инструкциями не понижается автоматически.
   Для сравнения доступен SearchIndex(use_search_representation=False).
   Повторяемая offline-проверка:
   `python -m app.rag.evaluate --documents-root PATH --cases
   docs/travel-retrieval-cases.json --output tmp/comparison.json`.
   Проверяем основной источник и группы страниц, а не правильность ответа.
   Это маленький набор разработки, не независимый бенчмарк качества модели.
   Добавлен ограниченный добор (app/rag/retrieve.py): начальные top-k, затем
   кандидаты из top-12 того же документа, версии и набора чанков. Сигналы:
   высокий ранг, соседняя страница или совпадающий раздел; порог 25% от
   лучшего BM25. Типы image/mixed без визуального вопроса и оглавления
   не добавляются. По умолчанию максимум 6 целых чанков / 12000 символов
   с подписями источников; точечные вопросы о графике/телефоне не расширяются.
   Лимит символов не является лимитом токенов провайдера.
   В боте добор включён; offline-просмотр: app.rag.inspect --expand.
   Нет обрезки текста, записи новых чанков или вызовов LLM внутри retrieval.
   Системный промпт и модель при сравнении ответов не менялись.
   Ограничение: mixed пока исключается консервативно. Для корпусов, где mixed
   содержит текстовые инструкции, нужно уточнить отбор по составу элементов.
5. **Подготовка vision-ответа.** Сборщик контекста с текстом и изображениями,
   ограничениями размера и fallback. Payload проверять моками; реальные вызовы
   отложить до появления ключа и подтверждения возможностей провайдера.
6. **Отложенная проверка моделями.** Владелец ключа повторно обрабатывает
   характерные страницы, проверяет OCR, подписи, ветвления, новые описания,
   retrieval и ответы end-to-end. До этого не объявлять качество vision доказанным.

Каждый шаг: небольшой коммит, offline-проверки и запись фактического результата.
Ни смена модели, ни увеличение top-k сами по себе не исправляют неверную транскрипцию.
