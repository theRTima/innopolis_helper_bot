# Аналитика обращений и задачи поддержки

Бот записывает вопрос, исход ответа и явное решение пользователя. Отдельный
обработчик объединяет похожие вопросы в темы. Панель показывает, сколько людей
столкнулось с проблемой и что изменилось после исправления. Наблюдаемые факты
отделены от гипотезы о причине.

## Запуск

У Alembic одна вершина для таблиц `analytics`, `question_analytics` и
`ticket_jobs`. Примените миграции и запустите разметку и панель:

```bash
alembic upgrade head
python -m app.analytics --watch
python -m uvicorn app.analytics.web:app --host 127.0.0.1 --port 8002
```

В Docker после основного запуска бота:

```bash
docker compose --profile analytics up -d analytics analytics-labeler
```

Панель будет доступна по `http://127.0.0.1:8002/`. Вход — HTTP Basic с
`ANALYTICS_USERNAME` (по умолчанию `admin`) и `ANALYTICS_PASSWORD`. За пределами
локальной машины используйте HTTPS и ограничение доступа. Разметчик читает ту
же БД и вызывает настроенную модель `LLM_*`; ответ бота его не ждёт. Для MVP
запускайте один разметчик на базу. Ошибочный ответ модели оставляет вопрос для
повторного прохода.

Для просмотра вымышленных карточек без БД и токенов:

```powershell
$env:ANALYTICS_DEMO = "1"
python -m uvicorn app.analytics.web:app --host 127.0.0.1 --port 8002
```

Этот режим не создаёт задачи. Для полного офлайн-пути с одноразовой БД:

```bash
python scripts/demo_ticket_flow.py
```

Скрипт показывает «вопрос → не решено → тикет» и «три похожих вопроса →
карточка → одна задача → сравнение до и после закрытия». Данные вымышлены;
внешняя тикет-система не вызывается.

## Личные заявки

Пользователь может написать `/operator` или «оператор». После отметки
«Вопрос не решён» он может нажать «Создать заявку» под ответом. Сама отметка
«Не решено», отсутствие источника и показанная ссылка поддержки тикет не создают.
Запрос сразу сохраняется в очереди, поэтому ответ бота не ждёт тикет-систему.
После подтверждённого создания фоновый обработчик присылает пользователю
внешний номер и статус. Повторное нажатие возвращает существующий запрос.

Ссылка `SUPPORT_URL` записывает отдельное событие «предложена ссылка».
«Запрошена поддержка», «тикет создан» и «доставка не удалась» учитываются
отдельно. `delivered` выставляется только после получения внешнего ID.
Неопределённый результат сетевого запроса остаётся в состоянии `uncertain`:
обработчик не отправляет второй `create`, пока сотрудник не сверит результат.

В тикет уходят локальный `question_id`, вопрос, ответ бота, названия и страницы
использованных источников и до восьми последних сообщений этого чата. Перед
отправкой из текста скрываются распознаваемые адреса почты, телефоны, ссылки
и `@`-имена. Telegram ID и контакты пользователя в провайдера не передаются.
Фильтрация ограничена распознаваемыми шаблонами; для реальных данных проверьте
её вместе с политикой обработки обращений вашей команды.

## Задачи из аналитики

Карточка появляется от трёх похожих вопросов минимум двух пользователей.
Сотрудник видит тему, период, число вопросов и людей, прошлый период,
нерешённые ответы, обращения без подтверждённых источников, обезличенные примеры,
документы и отдельную гипотезу о причине. При включённой интеграции примеры
видны авторизованному сотруднику перед подтверждением задачи. Кнопка
«Подтвердить задачу» отправляет защищённую форму; сервер заново проверяет
карточку и ставит в очередь одну задачу для темы. Новые вопросы обновляют
показатели темы, не создавая вторую задачу.

В задаче сохраняются агрегаты и очищенные примеры. Локальная БД хранит связь
темы с внешним ID, ссылкой и статусом. Обработчик опрашивает статусы созданных
задач не чаще одного раза в пять минут. После закрытия панель сравнивает
полные равные периоды до и после: вопросы и нерешённые ответы. Изменение
показателей само по себе не доказывает причину.

## Провайдер и фоновый обработчик

Если тикет-системы пока нет, задайте `TICKET_PROVIDER=demo`. Локальный
провайдер выдаёт стабильные номера `DEMO-*` без API-ключа:

```bash
python -m app.tickets.worker --watch 30
docker compose up -d ticket-worker
```

Для реальной системы выберите `TICKET_PROVIDER=jsm`, `zendesk` или `usedesk`,
заполните `TICKET_BASE_URL`, `TICKET_API_TOKEN` и при необходимости:

| Система | Дополнительные настройки |
| --- | --- |
| Jira Service Management | `JIRA_SERVICE_DESK_ID`, `JIRA_REQUEST_TYPE_ID`; `TICKET_EMAIL` для Basic auth |
| Zendesk | `TICKET_EMAIL` для API token auth; без него используется Bearer token |
| Usedesk | `USEDESK_CHANNEL_ID`, `TICKET_WEB_BASE_URL` при необходимости |

Контракты Jira Service Management, Zendesk и Usedesk проверены тестами с
подменённым HTTP. Jira Service Management дополнительно проверена через живой
API тестового проекта 15.11.2026: адаптер создал заявку и прочитал её статус.
Zendesk и Usedesk через живой API пока не проверялись. Для подключения другого
проекта нужны базовый адрес, токен с правами на создание и чтение тикетов, а для
Jira — ID сервисного проекта и типа запроса. Проверьте поля проекта, статусы,
ссылку на тикет и права бота на приватные комментарии. Токены задаются только
через окружение; локальный `.env` не добавляется в Git.

## Показатели

Единица подсчёта — сохранённое сообщение с вопросом; пользователи считаются
без повторов. «Доля подтверждённо решённых вопросов боту» имеет знаменатель
только из обработанных и доставленных ответов с известным типом результата.
Подавленные лимитами и недоставленные ответы в неё не входят. Предложенная
ссылка поддержки не считается запросом оператора. Старые отметки `delivered`
без связанного внешнего ID считаются показанной ссылкой, а не тикетом. Исходы
старых строк без подтверждения остаются неизвестными.

Долю автоматизации **всей поддержки** панель не показывает, пока нет данных об
общем потоке тикетов из внешней системы. Grafana использует агрегированные
представления; после миграции обновите их:

```bash
docker compose run --rm --no-deps bot python scripts/setup_grafana_reader.py
```

`ANALYTICS_AREAS_FILE` может задать JSON-словарь областей продукта. Коды
областей должны быть стабильными: старая разметка не меняется при смене файла.
