# Полнота и задержка ответа

## Текущий режим: ограниченный thinking

После предыдущего эксперимента thinking включён обратно для OpenCode Go /
qwen3.8-flash. Дефолт: `enable_thinking=true`, `thinking_budget=512`,
`max_completion_tokens=1400` (thinking + ответ). Контекст не менялся.

Пять вопросов: 6,60–15,94 с, медиана 12,09 с, всего 15122 токена,
из них reasoning=1791. По отдельным запросам reasoning: 124, 459, 237,
459, 512. Все finish_reason=stop. Один запрос достиг ровно 512;
в этом прогоне OpenCode соблюдал переданный thinking-бюджет.
Это пять одиночных замеров, не SLA и не доказательство надёжности лимита
при всех будущих маршрутах провайдера. Точность ещё требует независимой оценки.
Thinking помогает, но не гарантирует отсутствие домыслов/ошибок исходных данных.

Почему не только reasoning_effort=low: upstream описывает low как бюджет 4096,
а reasoning_effort и thinking_budget для Qwen3.8 нельзя задавать одновременно.
Поэтому отправляется численный бюджет, без reasoning_effort:
https://www.alibabacloud.com/help/en/model-studio/qwen-api-via-openai-chat-completions
max_tokens ограничивает не всегда весь выход; max_completion_tokens включает
рассуждение и ответ. Поддержка именно OpenCode проверялась экспериментом.

Настройки:

```dotenv
LLM_ENABLE_THINKING=auto
LLM_THINKING_BUDGET=512
ANSWER_MAX_COMPLETION_TOKENS=1400
```

auto выбирает ограниченный thinking только для проверенной пары host/model.
false оставляет быстрый режим без thinking. Для остальных провайдеров auto
не отправляет специальные параметры; явное true/budget требует поддержки API.
ANSWER_MAX_TOKENS остаётся для legacy/non-thinking-ветки; при ограниченном thinking
используется отдельный общий лимит ANSWER_MAX_COMPLETION_TOKENS. Нельзя поставить
общий лимит <= thinking-бюджета. Диапазон настраиваемого бюджета: 1–4096.
Ответ с finish_reason=length помечается как неполный, без автоматического повтора.

## История предыдущего эксперимента: thinking off

Корпус и контекст не менялись: 25 готовых чанков, до 6 источников / 12000 символов.
Новый промпт требует объединять релевантные источники, заканчивать инструкции,
разделять роли и ветвления, оговаривать границы знаний, не домысливать граф.
Это требования к генерации, не новые факты о командировке.

Параметр `enable_thinking=false` проверен на текущем OpenCode Go / qwen3.8-flash.
В 5 запросах и двух дополнительных сложных проверках провайдер сообщил reasoning=0.
Upstream API: https://www.alibabacloud.com/help/en/model-studio/qwen-api-via-openai-chat-completions
Поддержку промежуточного провайдера подтвердил именно эксперимент.

## Измерения (одиночные запросы, без нагрузки)

| Пять одинаковых вопросов, одинаковый контекст | Thinking по умолчанию | Thinking выключен, промпт v1 |
| --- | --- | --- |
| Задержка | 5,0–111,1 с | 4,1–10,0 с |
| Медиана | 40,3 с | 6,7 с |
| Входные токены | 9886 | 10656 |
| Все токены | 27409 | 12866 |
| Reasoning | 16402 | 0 |

После первой проверки усилен запрет на домысливание ролей и связей (промпт v2).
Повторены только два сложных вопроса: 4,67 и 8,70 с, 5835 токенов вместе,
reasoning=0. Остальные три вопроса на v2 не повторялись. Полнота/точность требует
независимой проверки, это не доказательство отсутствия ошибок. В первом быстром
прогоне модель ошибочно приписала офис-менеджеру согласующую роль; в повторной
проверке это исправилось. Неоднозначность и пропуски исходной схемы остаются.

## Настройки

В предыдущем эксперименте auto выключал thinking; эта настройка заменена
ограниченным thinking, описанным выше. Если провайдер не принимает параметр,
ошибка не скрывается автоматическим дорогим повтором.

SDK retries=0; HTTP timeout=20 с; общий asyncio deadline=20 с на генерацию.
Это ограничение ожидания клиента, не гарантия отмены вычислений/списаний на сервере.
При таймауте используется существующий обработчик ошибки бота.
Скрытый reasoning не выдаётся пользователю вместо пустого ответа.

## Что оптимизировать дальше

Сейчас retrieval — локальный BM25 по 25 чанкам. Измерять его отдельно от сетевого
ожидания, prefill и генерации. Векторная БД меняет стоимость поиска, но не устраняет
время reasoning на стороне модели. На больших корпусах нужны фильтры по проекту,
версии и правам, гибридный поиск и прежний ограниченный бюджет контекста.
Не отправлять больше текста только потому, что база выросла.

Следующие замеры: новые формулировки и документы, прогрев/холодный запуск,
параллельные пользователи, p50/p95 и стоимость. Не считать пять запросов p95/SLA.
Streaming улучшит время до первого текста, но не исправит точность и не сократит
полную генерацию сам по себе. Текущий рабочий кандидат — thinking с бюджетом 512,
один запрос и ограниченный контекст. Повышать бюджет следует только после
проверки полноты и задержки, без автоматического дорогого повтора.
